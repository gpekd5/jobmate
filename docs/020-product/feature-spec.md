## 현재 구현 범위 (#8·#9·#6)

- 루프백 로컬 단일 사용자 환경에서 PDF/DOCX 비공개 업로드·삭제, 선택 GitHub README, 선호조건, 목적별 동의, 명시적 비동기 AI 추출, 초안 수정·확정/버전 관리를 제공한다. 업로드는 AI 호출을 하지 않는다.
- 확정 프로필·JD 비교, Java 가중치 35/35/20/10, 근거별 MATCH/PARTIAL/GAP/UNKNOWN, 버전 캐시/중복 방지/누적 $5 선점 가드를 구현한다. AI 키·동의·설정·예산 없이는 외부 호출을 하지 않는다. 근거가 부족하면 점수는 null이다.
- 모바일 추천 피드/상세는 실제 API 상태·점수·강점·부족·미확인을 사용한다. 기존 전체 공고 검색은 유지한다. READ/UNREAD·NEW는 #11과 함께 후속이며 가짜 상태를 넣지 않는다.
- #7 자동 수집은 제외다. 현재 로컬 추천 갱신 60초 회차마다 모집 중·현재 버전 미분석 후보 최신 200개에서 최대 10개, 자동 20개/일, 개별 3개/일로 제한한다. 로그인·AWS 배포·실제 유료 모델 품질 검증도 이번 범위 밖이다.
- 파일 검증은 보수적이며 DOCX 외부 하이퍼링크도 거절한다. OCR은 없다. 정규식 마스킹의 한계, 저장/삭제 방식과 현재 확정 API는 [API 명세 §4~5](../030-api/api-spec.md), 실행 설정은 [로컬 개발](../010-getting-started/local-development.md)을 따른다. 아래 장기 요구사항을 현재 구현 완료로 해석하지 않는다.

## 1. 서비스 정의

**JobMate = 이력서·포트폴리오 기반 AI 맞춤 채용공고 자동 추천 서비스.** [확정]

사용자는 이력서(필수), 포트폴리오(선택), 지원 희망 직무(선택), 지역(선택)을 등록한다. JobMate는 승인된 출처에서 신규/변경 채용공고를 자동 수집하고, **담당업무·지원자격·우대사항까지** 가능한 범위에서 정리한다. 그런 뒤 사용자 경험과 채용 요건을 비교해 **적합도 0~100%와 그 이유**를 보여준다.

사용자가 채용 사이트를 매번 찾아다니거나 공고를 하나씩 입력하는 것이 기본 이용 흐름이 **아니다**. 수동 공고 등록은 외부 API가 준비되지 않은 개발 환경의 보조 기능이다.

### 1.1 성공 모습

1. 처음 방문해 이력서를 올리고, 포트폴리오·희망 직무·지역을 선택적으로 입력한다.
2. 분석된 기술·경력·프로젝트 사실을 **사용자가 검토·수정·확정**한다.
3. 이후 자동 수집된 공고에서 나에게 맞는 것부터 추천받는다.
4. 카드에서 **적합도 %, 일치 근거, 부족/미확인 요건, 출처, 공고 최신화 시각**을 확인한다.
5. 공고 상세에서 담당업무·지원자격·우대사항을 원문 출처와 대조하고, 실제 지원은 원문 사이트에서 한다.

### 1.2 제품 원칙

- **추천 중심:** 메인 화면은 전체 공고 검색창보다 **맞춤 추천 피드**가 먼저다. 검색/필터는 보조 기능이다.
- **원문 근거:** 수집한 사실, AI가 추출한 사실, AI의 해석을 구분한다. 공고나 이력서에 없는 기술·성과를 채우지 않는다.
- **자격 vs 우대:** `필수 자격`, `우대 사항`, `담당업무`를 서로 다른 요소로 관리한다.
- **퍼센트의 의미:** 87%는 **내 경험과 공고 요건에 대한 시스템 내부 적합도 점수**다. 합격 확률, 합격 보장, 기업 평가 점수가 아니다.
- **미확인 표시:** 상세 JD가 없거나 근거가 부족하면 정확한 척하지 않고 `분석 불충분` 또는 미확인 요건을 보인다.
- **모바일 우선:** 갤럭시 S23 등 좁은 화면부터 설계하고 넓은 화면으로 확장한다. 별도 네이티브 앱은 현재 범위가 아니다.
- **데이터·비용 최소화:** 공고 상세 수집 권리, 이력서 개인정보, LLM 전송 동의, 호출 비용을 먼저 관리한다.

## 2. 핵심 사용자 흐름

### 2.1 첫 사용

```text
회원 접근(로컬 개발에서는 제한된 테스트 환경)
  → 이력서 PDF/DOCX 업로드(필수)
  → 포트폴리오 파일 또는 URL 등록(선택)
  → 희망 직무/지역/근무조건 선택(모두 선택)
  → 문서는 NOT_ANALYZED로 보관(이 시점에는 AI 호출하지 않음)
  → 사용자가 AI 분석하기 클릭(별도 외부 전송 동의 확인)
  → ANALYZING → ANALYZED 또는 FAILED
  → AI가 경력/기술/프로젝트 정보 추출
  → '확인된 프로필' 화면에서 사용자가 검토·수정
  → 자동 수집 공고와 매칭
  → 적합도 높은 공고부터 추천
```

- 문서 업로드 성공과 **외부 LLM 분석 동의는 별도**다. 동의 없이 제3자 AI에 문서 원문을 전송하지 않는다.
- 파일을 올리는 것만으로 AI를 호출하지 않는다. 문서별 상태는 `NOT_ANALYZED → ANALYZING → ANALYZED`이고 실패 시 `FAILED`; `ANALYZED`여도 프로필 확정은 별도다. 사용자가 분석 버튼을 눌렀을 때만 AI 추출 요청을 시작한다.
- 문서 분석 실패 시 업로드 상태와 오류를 보여주며 사용자가 버튼을 다시 눌러 재시도하거나 프로필 정보를 직접 보완할 수 있어야 한다. 기존 확정 프로필은 새 문서 업로드만으로 변경되지 않는다.
- 희망 직무·지역을 선택하지 않아도 추천은 가능해야 한다. 선택하지 않은 항목으로 사용자를 불이익 처리하지 않는다.

### 2.2 재방문/반복 수집

```text
수집 스케줄 실행 → 허용된 제공처 API 조회
  → 신규/변경/마감 확인 → 데이터 정규화·중복 제거
  → 허용된 상세 JD 확보/요건 추출
  → 폭넓은 Java 후보 평가(탈락 공고도 보관) → 예산 내 AI 의미 비교 → 재현 가능한 적합도 산정
  → 결과 저장·최신화 → 추천 피드에서 확인
```

- 페이지를 새로 열 때마다 모든 공고를 LLM으로 재분석하지 않는다.
- 프로필·공고 원문·요건 추출·점수 정책이 변경되면 필요한 추천만 재계산한다.
- 수집 실패, 이용량 제한, 제공처 상세 원문 부재와 매칭 실패는 각각 다른 상태로 관리한다.

## 4. 상세 기능 요구사항

### F-01~F-04. 이력서·포트폴리오·프로필

**입력 [확정]**
- 이력서 1개 이상 필요(현재 추천 기준 이력서는 하나를 활성 버전으로 지정). 최초 파일은 PDF/DOCX를 기본 검토한다. 업로드 제한 크기·지원 파일 형식은 착수 시 보안 검토 후 확정한다.
- 포트폴리오는 선택. PDF/DOCX 등 파일 및 GitHub/포트폴리오 URL 지원을 계획한다. 링크를 입력했다고 **전체 GitHub 계정이나 비공개 저장소를 자동 수집하지 않는다**.
- 지원 희망 직무/지역은 선택. 근무형태, 연봉, 경력 수준, 출장·파견 제한 등은 추가 선택 조건이다.

**추출·확정 [설계안]**
- 이력서/포트폴리오에서 `workExperiences`, `skills`, `projects`, `education`, `certifications` 등 분석한다.
- 기술별로 **업무 경험 / 개인·팀 프로젝트 / 학습**을 구분하며, 같은 이름의 기술이라고 실무 경력을 자동 합산하지 않는다.
- 추출 근거(문서 ID, 인용 가능한 구간/요약)와 `confidence`, `verified` 여부를 기록한다. 수치·연차가 불명확하면 `unknown`으로 둔다.
- **업로드 = AI 미호출.** 각 문서는 처음 `NOT_ANALYZED`, 사용자가 직접 'AI 분석하기' 버튼을 누르면 `ANALYZING`, 성공 `ANALYZED`, 실패 `FAILED`이며 명시적 재시도를 지원한다. 분석 완료와 사용자 프로필 확정은 서로 다른 상태다.
- 분석 초안은 자동으로 **사용자 확정 프로필**을 덮어쓰지 않는다. 수정/확정 후 매칭에 사용한다. 새 이력서를 올려도 이전 확정 프로필을 유지하고 새 문서의 분석/확정이 끝난 뒤 변경한다.
- 업로드 교체·삭제 시 이전 파일/추출 텍스트/캐시/관련 분석 데이터의 처리 정책을 적용한다.

**인증/보안 [필수]**
- 본인 소유 데이터만 조회·변경·삭제. 로그인 구현 전에는 **루프백 로컬 개발 전용**으로만 프로필 API를 노출한다.
- 외부 AI 전송에는 별도 명시적 동의와 허용 범위 기록이 필요하다. 동의하지 않으면 외부 AI 호출 없이 수동 입력 또는 별도로 허용된 로컬 분석만 제공한다.
- 이력서 전문, 연락처, 이메일, 주소, 계좌 등은 로그에 기록하지 않는다.

### F-05~F-07. 채용공고 자동 수집과 JD 정규화

**수집 대상**
- 기본 메타데이터: 출처, 외부 공고 ID, 원문 URL, 회사명, 공고명, 직무, 근무지, 모집 상태, 게시·수정·마감 시각, 경력/학력/고용 형태.
- **상세 JD [확정]: 담당업무(responsibilities), 필수 지원자격(requiredQualifications), 우대사항(preferredQualifications), 기술스택(skills), 근무조건(workConditions).**
- 상세 JD 본문이 허용된 출처에서 제공되지 않으면 **`UNAVAILABLE`**로 표시. 없는 내용을 제목·키워드에서 추측해 자격 요건으로 기록하지 않는다.
- 각 필드의 `출처·원문 링크·확보 시각·정규화 상태·추출 근거`를 보존한다. 원문 텍스트의 저장/재가공은 제공처 이용조건에 따라 제한한다.

**데이터 수명**
- `source + externalJobId`를 우선 고유 식별자로 사용. 같은 출처의 변경 공고는 업데이트한다.
- 서로 다른 출처의 동일 채용은 잘못 합치지 않도록 안전한 후보 묶음만 제공(자동 병합 정책은 추후 확정).
- 마감일·상시채용·공식 상태를 구분하고, 수집 실패를 **공고 마감**으로 오인하지 않는다.
- 스케줄러는 **승인된 제공처만** 호출하고 요청량·rate limit·재시도·멱등성·최신화 시각을 관리한다.
- 외부 사이트 HTML 무단 스크래핑·인증 우회·차단 회피는 구현하지 않는다. 자동 수집이 본질이지만 **허용된 범위에서만** 실현한다.

**공식 제공처 조사 상태 (2026-11-20 기준)**
- 사람인 [공식 채용공고 API](https://oapi.saramin.co.kr/guide/job-search): 게시/마감·회사·직무·경력·학력·키워드 등을 제공하나, 명세상 **담당업무/필수·우대사항 상세 원문 제공은 확인되지 않음**. [이용자 주의사항](https://oapi.saramin.co.kr/caution)과 API 승인 조건 확인 필수.
- 원티드 [OpenAPI](https://openapi.wanted.jobs/): 이용 목적 확인 및 **인증 신청 필요**. 사용권한·세부 필드는 승인 시 검증한다.
- 잡코리아 [API 안내](https://www.jobkorea.co.kr/service/api): 자격요건·상세요강 URL 제공을 설명하지만, 상세 페이지 원문을 저장·AI 분석할 수 있다는 의미는 아니다. 이용 승인/범위를 확인한다.
- **상세 JD를 합법적으로 확보하지 못하면:** 수집된 기본 정보·직무 코드의 부분 비교만 보여주고, 상세 적합도에 `근거 부족`을 명시한다. 개발 중에는 자체 작성/사용자 제공 테스트 공고를 사용한다.

### F-08. 적합도 계산

**처리 순서 [설계안]**
1. 사용자가 확정한 프로필과 선택 희망 조건 확보.
2. 마감·직무·근무지역 등 **명확한 필터** 적용. 선택하지 않은 조건은 제외 사유로 사용하지 않는다.
3. 공고 JD의 담당업무/필수 지원자격/우대사항을 구조화하고 신뢰 가능한 출처만 매칭.
4. LLM으로 경험과 JD의 **의미적 부합도·근거·불확실성** 분석. 모델 호출 전 민감정보 최소화·명시 동의·비용 한도 적용.
5. 분석 결과를 검증된 규칙/가중치에 입력하여 **재현 가능한 0~100% 점수** 산출. 점수를 LLM의 임의 숫자 하나에 전적으로 맡기지 않는다.
6. 점수와 **일치 항목·부족 항목·미확인 항목·분석 기준 버전**을 저장한다.

**규칙**
- `MUST`(필수)와 `PREFERRED`(우대)는 가중치·처리 기준이 다르다.
- `MATCH / PARTIAL / GAP / UNKNOWN`을 구분한다. 정보가 없는 것은 `GAP`이 아니다.
- 장비용 C# 개발·제조업 경험을 관련 **전이 가능한 경험**으로 평가할 수 있지만 Java/Spring 상용 서비스 운영 경력이라고 허위 인정하지 않는다.
- 모집요건을 충족하지 못한 분명한 필수조건은 점수/추천 사유에 명확히 나타낸다. 선호 지역·직무가 선택된 경우 필터 우선순위 정책을 적용한다.
- **추출 불가능한 공고는 숫자 점수 대신 `INSUFFICIENT_DATA` 허용**. 모든 공고에 반드시 임의의 퍼센트를 붙이지 않는다.
- 신규·변경된 공고나 프로필 버전이 바뀐 경우만 필요 범위를 재평가한다. 페이지 조회마다 유료 분석을 다시 실행하지 않는다.
- `score`는 설명용 적합도이며 **합격 확률이 아니다**. 가중치·모델·품질 평가 기준은 구현 시 샘플로 조정한다.

### F-09. 추천 피드와 모바일 화면

- 기본 진입 화면: **추천순 채용공고 카드**. 카드에 회사명, 제목, 근무지, 출처, 마감, 적합도 %/분석 불충분, 긍정 근거 1~2개, 확인이 필요한 요건.
- 필터: 신규 공고, 마감 임박, 직무, 지역, 경력, 출처, 키워드. 추천순/최신순 정렬 지원. 선택하지 않은 선택 조건은 전체로 처리.
- 상세: 원문 링크, 담당업무, 필수 지원자격, 우대사항, 근거 있는 AI 분석 결과, `lastCollectedAt` / `analyzedAt`, 수집 제한/미확인 필드 표시.
- **S23 기준 Mobile First:** 좁은 화면에서 한 열 카드/스크롤/터치 가능한 필터와 버튼, 넓은 화면은 다중 컬럼으로 확장.
- AI 분석 완료 / AI 미분석 후보 / 수집 신규(NEW) / 읽음(READ)을 서로 다른 독립 상태로 표시한다. **NEW는 새로 수집된 공고**, 미확인(UNREAD)은 **본인이 상세 화면을 아직 열지 않은 공고**다.
- 사용자가 공고 카드 클릭 → 상세 정보 로드 성공 → 자동으로 사용자별 `viewedAt` 저장(멱등). 읽음 처리 버튼은 기본 제공하지 않는다. 목록에서 전체/미확인/확인 필터와 개수 표시, 필요 시 미확인으로 되돌리기 동작을 제공한다. NEW/수정됨 여부는 읽음과 분리한다.
- 분석하지 않은 공고도 전체 목록/추가 탐색에서 보이며, 사용자는 개별 'AI 적합도 분석하기' 요청 가능(예산 범위 및 중복 호출 제한).
- 로딩·빈 결과·수집 지연·AI 분석 중·부분 데이터·API 실패·재시도 상태를 구분.

### F-10~F-15. 부가 기능·운영

- **F-10 관심/지원:** 사용자가 관심 공고 저장·해제, 지원 진행 상태와 메모를 관리한다. **실제 원문 사이트에 자동 지원하지 않는다**.
- **F-11 인증:** 공개 배포 전 카카오 로그인, 사용자별 데이터 격리, 민감 파일 접근·삭제·탈퇴, CSRF/CORS/세션 정책 검토.
- **F-12 기업 분석:** 사용자 요청 시 허용된 기업 정보만 조사하며 결과에 출처와 확인일을 표기한다.
- **F-13 자기소개서:** 공고를 선택하고 요청할 때만 초안을 생성한다. 없는 경력·성과를 만들어내지 않는다.
- **F-14 AI 관측:** 분석 성공/실패·지연·재시도·토큰·비용·품질 샘플과 정책 버전 관리. 원문 개인정보는 지표/로그에 남기지 않는다.
- **F-15 운영:** 저비용 AWS, HTTPS, DB 비공개, 백업, 최소 스케줄 운영, 모바일 실기기 검증.

## 7. 합의된 기본 정책 (2026-11-20)

다음은 **실제 구현 기본값으로 채택한 제품 정책**이다. 환경변수/설정으로 변경할 수 있어야 하며, 보안·법률·외부 API 조건은 반드시 별도로 검증한다. 수치와 가중치는 **초기 운영값**이지 분석 정확도를 검증한 값은 아니다.

### P-01. AI 공급자·호출 비용

- **OpenAI API**로 시작한다. 기존 계정에 있다고 사용자가 밝힌 **$5 크레딧을 먼저 활용**, 전체 월 지출 목표는 **약 1만 원 이하**. API 사용액은 ChatGPT 구독료와 별개이며 크레딧 사용 가능 여부/만료는 실제 계정에서 확인한다.
- 별도 충전·유료 상향을 자동 수행하지 않는다. 애플리케이션 **누적 실험 비용 상한 $5**를 초기 하드 가드로 설정한다. 사용된 토큰 비용과 예약된 호출 예상 상한을 합산해 다음 호출 가능 여부를 선점 검사한다. 환율/실제 청구액 오차는 API 사업자 대시보드와 병행 확인한다.
- 저비용 OpenAI 모델을 우선 평가하고 **모델 이름은 환경설정**, 코드에 고정하지 않는다. 비용/정확도 검증 없이 고급 모델 자동 업그레이드 금지.
- 호출 전에 PII(연락처·이메일·상세 주소 등)를 마스킹/최소화. 제공업체와 분석 목적/전송 범위에 **사용자가 별도 동의**해야 외부 LLM 호출. 문서 업로드만으로 동의 처리하지 않는다.
- 요청당 시간 제한/재시도 최대 1회(일시적 오류에만), 동시 호출/토큰 상한, 비용 초과 시 분석 대기(`BUDGET_EXHAUSTED`) 처리. 원문과 모델 입력/출력 전문을 일반 로그에 남기지 않는다.

### P-02. 이력서·포트폴리오·문서 분석

- **PDF/DOCX, 파일당 최대 10 MiB**, 기본적으로 1개 활성 이력서 + 선택 포트폴리오 파일/공개 GitHub 리포지토리 URL. 업로드 파일 형식/확장자/MIME/실제 시그니처 확인, 파일명 무작위 저장 키 사용. 암호화·손상·미지원 파일에는 명확한 오류 반환. 매크로 포함 오피스 파일, 임의 스크립트 실행 금지.
- 파일 원본은 **사용자 전용 비공개 저장**하며 명시적 삭제/교체 전까지 보존한다. 서버 로그·Git·공개 정적 파일 경로에 두지 않는다.
- 업로드만 하면 `NOT_ANALYZED`. 명시적 '분석하기' 클릭 시에만 `ANALYZING` → `ANALYZED` 또는 `FAILED`. 분석 성공 시 DB에 추출 결과 저장, 사용자가 검토/수정 후 **별도로 프로필 확정**.
- 문서/사용자 삭제 시 활성 원본·추출 텍스트·관련 캐시/추천 데이터 삭제 또는 접근 차단 후 정리. **백업이 있다면 최대 30일 안에 만료·파기**(복원 시 삭제 기록 재적용); 실제 운영/백업 구성은 #11/#12에서 검증. 분석 완료 문서를 재분석하려면 명시적 버튼 요청.
- 새 파일 등록 시 기존 확정 프로필과 기존 추천은 **새 프로필 확정 전까지 유지**. 재분석은 같은 파일 버전+분석 정책 버전이면 기존 결과 재사용/중복 방지.
- 포트폴리오 링크는 사용자가 지정한 공개 GitHub 프로젝트로 기본 제한. **공개 README 등 명시된 허용 범위만** 필요한 경우 읽고 전체 계정/비공개 리포지토리 자동 탐색은 하지 않는다. URL 가져오기 구현 시 SSRF 방지 필수.

### P-03. 채용공고 수집과 상세 JD

- **사람인 공식 API부터 연결 검토**, 추가로 원티드/잡코리아는 승인·이용조건 확인 후 #17에서 확장한다.
- 수집은 기본 **6시간 간격(한국시간 00/06/12/18시)**, 제공처 호출 제한/허가량이 더 엄격하면 **제공처 조건이 우선**한다. 사람인 제공 필드만으로 상세 JD가 보장되지 않으며, 상세 HTML/저장/AI 재가공 권한이 없는 곳은 시도하지 않는다.
- 허용된 범위에서 수집한 공고 메타데이터는 중복 제거 후 DB에 보관하고, 신규/변경/마감만 갱신한다. 제공처의 삭제·보관 기한·철회 요청이 우선한다.
- 상세 JD 확보 시 담당업무·필수 지원자격·우대사항 분리. 확보하지 못한 공고는 `UNAVAILABLE`/부분 정보, **AI 점수 미산출도 허용**. 수집 실패를 공고 마감으로 처리하지 않는다.
- 이미지형 JD OCR, 임의 외부 링크 자동 추적, 사이트 접근 제한 우회는 **초기 제외**. 파일에서 정상적으로 추출 가능한 텍스트만 처리. 지원자 제공 문서/허용 테스트 공고로 개발 가능.

### P-04. 비용 제한·누락 방지형 추천

- **모든 수집 공고를 검색 가능하게 유지**(보관이 허용된 범위에서). AI 선별 탈락 = 공고 삭제/비노출이 아니다.
- Java 1차 후보 판단은 넓게 적용(직무 유사어·기술·경험·지역/조건). 명시적으로 마감되었거나 사용자가 강하게 제외한 조건 외에는 무리한 하드 필터링을 하지 않는다.
- AI 자동 분석은 **수집 실행당 최대 10건, 하루 자동 최대 20건**을 초기 상한으로 시작한다. 배정은 **우선 후보 80%, 추가 탐색 후보 20%**를 기본값으로 하되 후보 부족 시 다른 그룹에 재배정한다. 신규/변경 공고 우선.
- 사용자가 미분석 공고에서 직접 누른 **개별 AI 분석은 하루 최대 3건**, 잔여 예산이 있을 때만. 미분석/비용 대기/재분석 불가 상태를 구분한다.
- 동일 프로필 버전+공고 내용 버전+점수 정책 버전+모델/프롬프트 버전은 결과 캐시 재사용. 이력서 재분석은 사용자가 버튼 클릭 시에만 수행; 새 공고 수집 시 문서 원본을 재분석하지 않는다.
- 결과는 **자동 분석 완료 / 추가 탐색(미분석) / 마감/제외** 구분. 분석 여부와 추천 점수, 읽음 상태는 독립.

### P-05. 적합도 초기 산정 정책

- 점수는 **담당업무·직무 경험 35%, 필수 지원자격 35%, 우대사항 20%, 근무조건 10%**의 기준 가중치로 시작한다. 항목별 AI 의미 분석 결과(`MATCH/PARTIAL/GAP/UNKNOWN`)를 Java 검증 규칙으로 점수화; LLM이 자유롭게 반환한 %를 그대로 노출하지 않는다.
- **명시적인 필수 자격 부족은 감점 + 별도 '필수조건 미충족' 경고**이며 원칙적으로 전체 목록에서 삭제하지 않는다. 사용자가 명시한 강한 제외 조건(예: 특정 지역 제외)만 자동 추천에서 제외할 수 있다.
- **최소 근거 기준:** 검증 가능한 공고 JD의 서로 다른 구체 요건/담당업무가 2개 이상이고, 그중 1개 이상은 담당업무 또는 필수 지원자격이어야 하며, 사용자 확정 프로필이 있어야 숫자 적합도 산출 가능. 부족하면 `score=null`, `INSUFFICIENT_DATA`.
- 제공되지 않은 항목/증거 불확실성은 `UNKNOWN`으로 처리해 불일치로 간주하지 않으며, 제공되지 않은 점수 범주는 분모에서 제외한 뒤 나머지를 정규화한다. 이때 평가에 사용된 **근거 항목 수·분석 범위와 미확인 요건을 함께 표시**해 점수 과대해석을 방지한다.
- `MATCH=1`, `PARTIAL=0.5`, `GAP=0`; `UNKNOWN`은 임의 0점이 아니라 **미확인**으로 보유하고 근거 불충분 임계값에 따라 점수 미산출 처리. 항목별 평균 후 범주 가중치 적용, 최종 0~100 정수 반올림. `scoringVersion=v1` 기록.
- 이 점수는 **합격 확률이 아니다**. 초기 가중치·분류가 실제 추천 품질에 적절한지는 #9에서 샘플 평가로 검증하고 필요할 때 버전 변경한다.

### P-06. 읽음 상태·추천 화면

- 새 수집 공고는 **미확인(UNREAD)**. 사용자가 추천/전체 공고 카드 클릭 → **상세 내용 로드 성공** 시 사용자별 `viewedAt`을 멱등 저장해 **확인(READ)**. 따로 '확인 완료' 버튼을 두지 않는다.
- 목록에서 **전체/미확인/확인** 필터와 개수를 제공한다. 필요하면 '미확인으로 되돌리기' 동작을 제공하되 기본 클릭으로 읽음 처리하는 규칙은 유지.
- **NEW(최근 수집됨)**, **READ/UNREAD(사용자 확인)**, **ANALYZED/NOT_ANALYZED(공고 AI 분석 상태)**는 서로 다른 개념. 단순 공고 내용 수정은 사용자 읽음 상태를 초기화하지 않고 별도 '업데이트됨' 배지를 표시한다.
- 카드/상세에서 AI 점수가 없는 공고는 `미분석/정보 부족`으로 표시하고 **개별 분석하기** 선택 제공. S23 모바일 우선 반응형 UI.

### P-07. 인증·운영·알림

- 최초 개발은 **루프백 로컬 단일 사용자**로 진행하되 User 소유권(ID)을 모든 개인 문서·프로필·읽음/관심·점수에 적용할 수 있게 설계한다.
- **카카오 OAuth2 + Spring Security 서버 세션**을 공개 배포 전 기본 인증으로 사용한다. 쿠키는 `HttpOnly/Secure/SameSite`와 CSRF 대응, 사용자별 소유권 체크를 적용한다. JWT 의무화 없음.
- **로컬 개인 문서 기능을 공개 인터넷/동일 와이파이에 무인증으로 노출하지 않는다.** Vite의 `--host 0.0.0.0` 테스트는 실제 이력서·문서가 없는 개발 상태에서만 하거나 사전에 접근 보호를 적용한다.
- 초기는 사이트 내 **새 공고/미확인 건수 표시**로 충분하다. 푸시·이메일·카카오 알림은 후속. 퍼블릭 HTTPS 배포 전에 인증·비밀키·파일 보호·백업/삭제 검증을 필수로 한다.

### 외부에 의존하는 확인 항목 (임의 확정 불가)

1. 채용 플랫폼 **실제 API 접근 승인, 상세 JD 취득·저장·AI 재가공 허용 범위** (#7, #17).
2. OpenAI API **실제 크레딧 사용 가능 여부/만료, 당시 사용 요금, 개인정보 처리 조건** (#8, #9).
3. 실제 백업 사업자·저장소가 **30일 파기와 삭제 복원 방지 정책을 준수하는지** (#11, #12).
4. 모델별 매칭 품질·초기 가중치의 정량적 타당성은 출시 전 샘플 검증 (#9, #13).

## 8. 대표 수락 시나리오

- [ ] 파일 업로드만 하면 `NOT_ANALYZED`로 남으며 AI 호출이 없다. 사용자가 분석 버튼을 눌러야 추출 결과가 나타나고 사용자 확인·수정 후 추천 기준으로 반영된다.
- [ ] 포트폴리오·희망 직무·지역을 **입력하지 않아도** 기본 추천 흐름을 진행할 수 있다.
- [ ] 공고의 **담당업무/필수/우대**가 허용된 출처에서 제공되면 각각 구분해 저장/표시한다.
- [ ] 상세 JD가 없는 공고에서는 근거 부족을 표시하고 임의의 필수자격이나 점수를 만들어내지 않는다.
- [ ] 동일 출처의 동일 공고를 다시 수집해도 중복 Row가 생기지 않고 변경 내용만 갱신된다.
- [ ] 신규 공고가 들어오면 문서 재분석 없이 넓게 후보 선정하고 예산 범위에서만 추천 재계산을 수행하며, 추천 %와 근거가 표시된다.
- [ ] 선별되지 않은 공고도 전체/추가 탐색 목록에 남고 개별 AI 분석 버튼을 사용할 수 있다.
- [ ] 카드 클릭 후 상세 로드 성공 시 사용자별 읽음으로 자동 변경되고 전체/미확인/확인 필터가 동작한다.
- [ ] API/LLM 실패·rate limit·동의 미제공 상황에서도 기존 데이터 및 사용자가 확정한 프로필이 보존된다.
- [ ] 모바일 좁은 화면에서 추천 카드와 필터, 상세/원문 이동을 사용할 수 있다.
- [ ] 인증 전에는 실제 개인정보를 외부 공개하지 않고 제3자 AI에 동의 없이 전송하지 않는다.

## 10. 공고 카탈로그 구현 범위 (#5·#6)

이번 작업은 MySQL 저장 → Spring 공고 API → React 모바일 탐색을 하나의 기능으로 구현한다. 이 문서의 전체 추천 제품이 완료됐다는 뜻은 아니다.

- 구현: 자체 예시 공고의 메타데이터와 담당업무·필수 자격·우대·기술·근무조건 저장, 상세 확보 상태·출처·시각, 변경 버전, 검색·필터·페이징·모바일 목록·상세·원문 링크.
- JD 목록 `null`은 미확인, `[]`는 명시적 해당 없음으로 구분한다. 제한되거나 확보하지 못한 본문을 추측·생성하지 않는다.
- 화면의 공고는 추천순이 아닌 전체 공고이며 모든 AI 상태는 **미분석**이다. 정보 부족 공고도 숨기지 않는다. 개발 입력은 로컬 프로파일에서만 가능하고 사용자용 수동 등록 UI를 만들지 않는다.
- #6 후속: #8의 문서·확정 프로필 흐름, #9의 추천 피드·적합도·근거·개별 분석과 비용 상태, 사용자 식별/인증에 연결된 READ/UNREAD 자동 기록·필터·개수·복귀 동작. NEW/업데이트/읽음/AI 상태를 임의로 같은 상태로 취급하지 않는다.
- 현재 제공하지 않는 개인 API나 추천 API를 호출하거나 가짜 성공·퍼센트·읽음 상태를 만들지 않는다. #6은 이번 작업으로 전체 완료 처리하지 않는다.
